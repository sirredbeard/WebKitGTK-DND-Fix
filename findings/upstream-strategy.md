# Upstream strategy: solve it at the WebKitGTK level

Written 2026-09-02, after picking the effort back up. This file takes a fresh
look at the problem. It does not delete or replace earlier findings. The
packaging and nested GUI work in `appimage-packaging.md`, `flatpak-gnome-web.md`,
`nested-gui.md`, `gui-automation-and-ci.md`, and `e2e-results.md` stays. It
taught us real things about the portal path. It is no longer the plan.

## The root cause is not the security fix. It is the missing test.

Michael Catanzaro disabled file access on 2025-12-03 in commit `89838b9164a1`
(`303828@main`). Read what he wrote on bug 303434 comment 0:

> This isn't implemented properly for WebKitGTK and most likely also not for
> other ports. My initial attempts to fix things have failed, so let's just
> completely disable it for now.

The disable commit is two files and five added lines:

- `Source/WebCore/dom/DataTransfer.h` +5/-0
- `LayoutTests/platform/gtk/editing/pasteboard/paste-image-does-not-reveal-file-url-expected.txt` added

Reverting that is trivial. Proving the revert is safe is the entire problem.
And WebKitGTK has no way to prove it, because of bug 157179.

### Bug 157179: [GTK] Drag and drop can't be tested with WebKitTestRunner

Filed 2016-04-29 by Carlos Garcia Campos. Status REOPENED. Still open after
nine years. Duplicates were still being filed against it as recently as
2025-07-01 (bugs 277403 and 277405, both closed as duplicates by Diego Pino).

Carlos diagnosed it in comment 0:

> the drag and drop context is not handling the synthetic events generated by
> the EventSenderProxy. So, for example, when we generate a GDK_MOTION_NOTIFY
> by EventSenderProxy::mouseMoveTo(), the GdkDragContext doesn't handle that
> event and DRAG_MOTION is not called preventing the rest of the drag and drop
> protocol from working properly.

Consequences we verified directly in `LayoutTests/platform/gtk/TestExpectations`:

- 42 expectation lines point at 157179.
- 50 lines total mention drag or dataTransfer.
- `fast/events/drop-with-file-paths.html` is skipped with the comment
  "'beginDragWithFiles' is only implemented in Mac. All other platforms skip
  this test."

`Tools/WebKitTestRunner/gtk/EventSenderProxyGtk.cpp` has 527 lines and
implements mouse, keyboard, wheel, and touch. It implements no drag entry
point at all. There is no `beginDragWithFiles`.

So the causal chain is:

1. GTK cannot test drag and drop.
2. Therefore no regression test guarded file access.
3. Therefore a file access bug (CVE-2025-13947) shipped.
4. Therefore the fix had to be a blunt global disable, because a narrow fix
   could not be proven.
5. Therefore it is still disabled today.

Fixing 157179 is not a detour. It is the thing that unblocks everything else.

## The plan

Three phases. Test infrastructure first, because it is the blocker, it is
independently valuable, and it is the cheapest thing to get reviewed.

### Phase 1: make drag and drop testable on GTK (bug 157179)

This is the keystone commit and it should be its own pull request, landed
before we ask for anything on file access.

Do not try to make synthetic GDK motion events drive `GdkDragContext`. That is
what failed in 2016 and it is the wrong layer. Cocoa does not do a real OS drag
in `beginDragWithFiles` either. It synthesizes the pasteboard and drives the
drag session directly.

#### Correction: WebKitTestRunner has no drag support on any platform

Checked in the tree, not assumed. `beginDragWithFiles` appears only in
`Tools/DumpRenderTree/mac/EventSendingController.mm`, the legacy WebKit1 test
runner. `Tools/WebKitTestRunner/EventSenderProxy.h` declares no drag entry
point for any port, and `Tools/WebKitTestRunner/mac/EventSenderProxy.mm` has
only mouse-dragged event types, not a file drag session.

So "implement `beginDragWithFiles` for GTK in WebKitTestRunner" would mean
inventing a cross-port testing API that Apple has never needed in WKTR. That is
a much larger review surface, it touches a shared header, and it invites
objections from reviewers who do not care about GTK. It is the wrong first ask.

`fast/events/drop-with-file-paths.html` is therefore not the right target
either. It is a DumpRenderTree-era test. Leave the skip alone for now and say
why in the bug.

#### The right seam: a GLib API test

`Tools/TestWebKitAPI/glib/WebKitGLib/WebViewTest.h` already provides everything
an end to end file drop test needs, and it is entirely within GTK maintainer
review scope:

- a real `WebKitWebView`
- `showInWindow()`, which creates a real `GtkWindow` and realizes the widget,
  so `DropTarget` is live. Runs fine under Xvfb.
- `loadHtml()` and `waitUntilLoadFinished()`
- `runJavaScriptAndWaitUntilFinished()`, which can read
  `dataTransfer.files.length` and `FileReader` output back out of the page

That last point is the whole game. The assertion happens in JavaScript, in the
web process, after a real IPC round trip from the UI process. It exercises
precisely the trust boundary we changed, which is "UIProcess set these
filenames" versus "the page wrote this uri-list".

Tests are registered with the `ADD_WK2_TEST` macro in
`Tools/TestWebKitAPI/glib/CMakeLists.txt` and listed in
`Tools/TestWebKitAPI/glib/PlatformGTK.cmake`, alongside existing suites such as
`TestWebViewEditor` and `TestContextMenu`. A new `TestDragAndDrop` belongs
there.

What still has to be built is the injection point. `DropTarget` takes a
`GtkWidget*` and works from a real `GdkDrop` or `GdkDragContext`, so a test
cannot simply construct one. Options, in order of preference:

1. A testing-only entry on `WebKitWebViewBase` that builds a `SelectionData`,
   calls `setFilenames()` on it to model a trusted external drop, and drives
   the existing `DropTarget` code path into
   `page->dragEntered`, `dragUpdated`, and `performDragOperation`.
2. Failing that, a small friend or internal accessor so the test can drive
   `DropTarget` directly.

Either way the production code path is the one under test. The hook supplies
the input that a file manager would normally supply. It must not bypass the
trust logic itself, or the test proves nothing.

Deliverables:

- The injection hook, kept as small and as clearly test-only as possible.
- `Tools/TestWebKitAPI/Tests/WebKit/WKWebView/gtk/TestDragAndDrop.cpp` with at
  minimum: a trusted external drop yields `dataTransfer.files.length >= 1` and
  the contents are readable; and a page-authored `file://` uri-list yields
  `files.length === 0`.
- Wire it into `PlatformGTK.cmake`.
- Do not try to unblock all 42 tests behind 157179 in this commit. Fix the file
  drop case, and say in the bug that the general synthetic-event problem
  remains.

## What this changes about our infrastructure

The AppImage was a stopover on the way to the Flatpak. The Flatpak was a way to
run a real browser for manual QA. Neither is a deliverable, and no reviewer will
ever see one. Debugging Flatpak module builds is not progress on this bug.

- Stop treating the nested GUI matrix as the gate. Keep the code and the
  findings. It is supplemental confidence, not the bar.
- The new bar is the in-tree test from Phase 1, which runs on EWS for free,
  forever, and which reviewers can run themselves.
- Azure compute is now for building WebKit and running `TestWebCore` plus
  layout tests. That is a much smaller machine and a much shorter job than
  packaging two bundles and booting nested VMs.
- This is also the honest answer to the budget problem. The reason we spent
  $554.26 in August was a runaway VM, but the reason the VM was that large was
  the packaging and nested GUI pipeline. Removing the pipeline removes the
  demand.

## First review round: Copilot bot, 2026-09-03

GitHub's Copilot reviewer left four inline comments on PR 73114 within the
hour. Three were valid and are fixed in tip `2fd5c6cb7ea7`, tree
`bc272e2a5ebe08e3027b1968d4995c60530acdc5`, squashed and force-pushed. One
was wrong and got a decline with a citation. All four replies are inline on

The catch that mattered: the GTK4 portal lambda converted GdkFileList URIs
to paths with a null hostname out parameter, the exact
g_filename_from_uri() pattern the commit message argues against. GTK will
deserialize a text/uri-list into a GdkFileList, so that list is not
portal-clean by construction, and a foreign-host file URI could have become
a local grant through the portal channel. Fix: localPathFromURIListLine()
is now a public static on SelectionData and the portal path calls it. One
predicate, both callers. The commit message portal paragraph gained a
sentence. Honest limit, stated in the reply: the real GdkFileList read path
is behind bug 157179, so no in-tree test goes red if that call site is
reverted. The predicate itself is pinned by
SelectionData.RemoteHostFileURIIsNotAGrant.

The other two accepted: TestWebCore include root narrowed from Source to
Source/WebKit with the test including <UIProcess/API/gtk/DropTargetState.h>,
and WebViewTest::dropFiles() now takes Vector<String>&& with WTF::move
instead of copying per drop.

The decline: the bot claimed g_cancellable_cancel(nullptr) emits a GLib
